# Gaia compatibility subsystem

Gaia loads static Linux x86-64 ELF programs and a limited Windows x64 PE32+ API subset. The kernel selects a personality at image load: Linux calls use the existing syscall dispatcher, self-contained Gaia PE images retain their original startup, and imported PE images receive the Win32 DLL runtime. POSIX service adapters use Gaia's existing services and return negative errors without changing `errno`.

The PE loader validates images, maps modules into the process address space, applies DIR64 relocations, resolves named and ordinal imports and forwarded exports, and initializes dependencies before their dependants. The process owns the module graph until its address space is reaped. DLL search currently checks the executable directory and `/system/win32`; dynamic modules are pinned until process exit. DLLs with PE TLS callbacks or delay imports are rejected. The x64 TEB uses GS, while Linux TLS uses FS.

The implemented Windows subset is listed by the `.def` files under `shims/win32`: console and basic file I/O, anonymous memory and heap operations, process and thread identifiers, threads, TLS, events, critical sections, basic environment variables, module lookup, windows, messages, and basic drawing and 32-bit DIB transfers. File sharing is not enforced, named synchronization objects and full Windows path semantics are absent, and `FreeLibrary` does not unload. DLL detach is delivered on normal process exit. Closing a running thread handle can retain its allocations until process exit. Exception handling, PE TLS callbacks, Windows process creation and many Win32 APIs remain unimplemented. Unsupported imports fail image loading rather than being silently substituted. GUI input uses Heimdall's existing IPC window services.

Linux supports a small static executable subset including low-address images, an auxiliary vector, FS TLS, file I/O and anonymous memory. Dynamic ELF interpreters, general glibc compatibility, Linux `clone`/complete pthread behavior and timed futex waits are not implemented. `AT_RANDOM` uses hardware RDRAND when available; its timing fallback is not a cryptographic entropy source.

Libraries declare `LIB_NAME`, `LIB_TYPE`, `LIB_FORMAT`, `LIB_ABI`, `LIB_SOURCES`, `LIB_DEPS`, and optionally `LIB_EXPORTS`, `LIB_ENTRY`, `LIB_CFLAGS` and `LIB_LDFLAGS` in a local `build.mk`. Source paths may refer to other files within userspace. Dependencies are named libraries, are cycle checked, and must use the same object format. Static archives and PE DLL/import libraries live under separate `build/userspace` trees. The packaging target includes registered DLLs in `/system/win32`.

Run `mingw32-make -j12 build-x86_64 BUILD_COMPAT_TESTS=1`, then `python3 tests/compatibility_test.py` under WSL/Linux for the selected Windows console, DLL, Linux static ELF, and GUI fixtures. `test-compat-host`, `tests/userspace_build_test.py`, and `tests/shim_build_test.py` provide focused host checks. The Linux fixture is built with the host Linux static toolchain; the Windows fixtures use the standard MinGW SDK and import libraries.

Format references: [Microsoft PE format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format), [Microsoft x64 calling convention](https://learn.microsoft.com/en-us/cpp/build/x64-calling-convention), and [Linux termios UAPI](https://github.com/torvalds/linux/blob/master/include/uapi/asm-generic/termbits.h).
